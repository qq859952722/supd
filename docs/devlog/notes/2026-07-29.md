### 关键技术点

- **dispatcher 不记录成功扩展运行**：supd.log 仅在扩展失败时记 ERROR/WARN；成功运行仅写入 `/tmp/supd-logs/extensions/<ext>/<run_id>.log`。排查 post_ready 是否执行需查扩展运行日志文件，而非 supd.log。
- **post_ready 异步时序**：HTTP 服务器在 goroutine 中 `net.Listen` 后立即回调 `addrReady` 打印第二段摘要，主 goroutine 同时启动 post_ready goroutine。由于 `net.Listen` 绑定极快（~1ms），两段摘要几乎同时出现，post_ready 的 3 秒执行完全在后台。
- **关机时仍等待异步 post_ready**：`dispatcher.GetConcurrencyManager().HasAnyRunning()` + `WaitForAllRunning` 确保关机前等待 post_ready 完成，再执行 GracefulShutdown（含 pre_shutdown 钩子）。

### 关键技术点

- `RunExtension`（extension_provider.go:372）是**异步执行模式**：预记录 `TaskRunning` 后立即返回 `run_id`，扩展在后台 goroutine 中执行。因此 queue full 的失败发生在 goroutine 中，不反映在 HTTP 响应（响应恒为 `state=running`），而是通过 runs API 查询。测试计划 F2 的原始预期「第 17 个返回 200 但 result.state=failed」基于同步假设，实际需查询 runs 历史验证。
- `TaskHistory.Add` 按 RunID 覆盖存储（`h.runs[result.RunID] = result`），随后调用 `lazyCleanupLocked`。若 result.StartedAt 为零值，会被立即删除——这是 lazyCleanup 的固有设计（删除超期记录），但要求所有 RecordRun 的 result 必须有非零 StartedAt。
- serialize 队列上限 16 是 **pendingRuns** 的上限：第 1 个直接执行，第 2-17 个进入队列（共 16），第 **18** 个才触发 queue full。测试计划原写 17 个是计算偏差。
