## 扩展 CWD/entry 解析根回归修复（v0.0.44 引入）

### 触发原因
用户反馈 192.168.31.190:7979 上**所有扩展启动失败**，报 `ReferenceError: could not load '<服务根>/run.js' - ENOENT`（如 filebrowser-updater）。怀疑是工作目录识别错误，要求先用实例测试，再分代码定位，并顺带分析各服务日志排查其他问题。

### 实例验证
- 触发 `filebrowser-updater` 扩展，日志显示 entry `run.js` 被解析到服务根目录 `/etc/supd/services/filebrowser/run.js`（不存在），而实际脚本位于 `/etc/supd/services/filebrowser/extensions/filebrowser-updater/run.js`。
- 线上 `meta.yaml` 使用相对 `entry: run.js`，运行期解析根错误导致全部扩展启动失败。

### 根因
v0.0.44「统一配置路径解析规则」提交（`12980ff`）修改了 `internal/extension/dispatcher.go` 的 `buildWorkDir`：

```go
// v0.0.44 之前（正确）：返回扩展自身目录
// 注释：工作目录为扩展自身目录（meta.yaml 所在目录），这样 entry 中的相对路径（如 run.sh）可以正确定位
return extDir

// v0.0.44（回归）：全局返回 baseDir，服务级返回服务根目录
if extEntry.ServiceName != "" {
    return filepath.Join(baseDir, "services", extEntry.ServiceName)
}
return baseDir
```

导致扩展进程 CWD 与相对 entry 的解析根从**扩展自身目录**错误改为**服务根/baseDir**。

### 修复
- `internal/extension/dispatcher.go`：`buildWorkDir` 恢复返回 `filepath.Dir(extEntry.ConfigPath)`（扩展自身目录）；script_tmp 仍创建供临时文件（不自动清理）
- `internal/api/extension_provider.go`：`RunExtension` 的 workDir 改为扩展目录；serviceDir 单独计算仅用于 `SUPD_SERVICE_DIR` 注入
- `internal/api/extension_handler.go`：导出/导入校验 `validateExtensionForExport` 的 entryRoot 改为扩展自身目录；`validateExtensionImport` 去掉 entryRoot 参数
- `internal/api/export_handler.go`：服务包内扩展校验的 entry 解析根改为扩展目录
- `internal/extension/run_context.go`：`WorkDir` 字段注释同步

## 镜像层增量更新优化（v0.0.48）

### 触发原因
用户希望更新镜像时尽量只拉取变化的 supd 二进制，减少镜像更新流量。

### 修改
- `Dockerfile` 与 `Dockerfile.debian` 将 tjs 包装脚本、supd 二进制和 tjs 二进制拆分为独立构建层。
- 使用 `COPY --link --chmod=755` 复制 supd/tjs，更新 supd 时最大化复用基础系统、tjs 和包装脚本层。
- 保持现有 GitHub Actions 的 `context: .`、`target: runtime`、Buildx 和 registry cache 配置不变；CI 下载的 `./tjs` 路径不变。

### CI 兼容性审查
- `docker/build-push-action@v7` 使用 BuildKit，支持 `COPY --link` 和 `--chmod`。
- Alpine 与 Debian 两条镜像 workflow 的构建上下文、Dockerfile、架构矩阵、tjs artifact 和镜像 target 均与修改后 Dockerfile 对齐。
- 按用户要求未执行本地构建，仅完成 workflow 与 Dockerfile 静态兼容性审查。
