# 2026-08-05 会话

## 服务日志前缀时间 bug 修复

### 触发原因
用户反馈 192.168.31.188:7979 上 dnscrypt-proxy 服务日志的前缀时间全部相同(都是查看时刻 19:35:16),不反映日志实际产生时间。日志内容实际时间跨度从 18:38 到 19:34,但前缀都是 19:35:16。

### 根因
`web/src/components/service/LogViewer.tsx` 长轮询批量获取日志时,所有行的 timestamp 被设为 `Date.now() / 1000`(当前接收时刻),而非日志实际产生时间。显示时用的就是这个错误时间,导致同批次日志前缀时间全部相同。

日志数据流:
1. 服务进程 stdout 输出
2. supd 捕获写入日志文件,格式 `[RFC3339] [level] message`
3. API `GET /api/services/{name}/logs` 返回 `{data: [{content: "[RFC3339] [level] message"}]}`,未单独提供 timestamp/level 字段
4. 前端 LogViewer 用 `Date.now()` 作 timestamp(错误),`detectLevel` 启发式识别级别(不准)

### 修复
新增 `parseLogContent()` 函数,从 content 解析:
- RFC3339 时间戳 → timestamp(支持纳秒截断到毫秒兜底,JS Date 仅支持毫秒精度)
- `[level]` → level(替代 detectLevel 启发式,更准确)
- 剩余内容 → message(去掉 supd 的 `[RFC3339] [level]` 前缀,避免与前端显示前缀重复)

解析失败时兜底(Date.now + detectLevel)。

### 修改文件
- `web/src/components/service/LogViewer.tsx`:新增 `parseLogContent` 函数,修改长轮询 map 逻辑用解析结果替代 `Date.now()`/`detectLevel`
