### 操作验收 O1~O10 证据索引
- **O1 全局多 operations 生成多操作**：`GET /api/operations` 返回 `check-software`、`update-software` 两个操作（+辅助扩展操作的独立验证用）。
- **O2 同扩展重复操作 ID 被拒**：构造 `dup-op-test-ext`（两个 action 各带 `operations: [dup-op]`）→ 热重载加载失败，操作列表**不含** `dup-op`；重启日志显式报 `actions[1].operations: duplicate operation id "dup-op" in extension`。
- **O3 不同全局扩展相同 ID 合并**：`merge-test-ext` 再注册 `check-software` → 列表仍 1 个按钮，`registrants=["merge-test-ext","operation-global-ext"]`，warning=`与首个注册者名称/样式不一致，已采用首个注册者`。
- **O4 服务扩展正确响应**：`check-software` Execution 含 `service/app-demo/operation-responder-ext` 的 `respond-check` Run `state=success`。
- **O5 Global 全部终态后才开始 Service**：同一 Execution 的 global Run `started_at=…18942`、service Run `started_at=…19249`，时间戳先后顺序成立。
- **O6 Global 失败仍执行后续 Global+Service**：`fail-op` 由 `fail-global-a-ext`(exit 1) + `fail-global-b-ext`(success) + service `fail-responder-ext` 响应；执行结果为 `global/fail-a failed`、`global/fail-b success`、`service/fail-responder success`。
- **O7 全局只执行一次，服务按服务执行一次**：`check-software` 单全局 Run（operation-global-ext）+ 单服务 Run（app-demo）。
- **O8 并发参数/Topic/Execution/Run ID 不串**：并发 POST `check-software`×2 + `update-software`×1 返回三个独立 execution_id/topic_id，各 topic 通知内容归属正确（更新/检查标签互不混淆）。
- **O9 concurrency replace 生效**：连续触发 `update-software` 3 次 → runs 历史出现 2 条 `canceled` + 1 条 `success`（replace 取消前任务）。
- **O10 重启中断呈现**：`slow-op`（sleep 30s）执行中 `kill -9 supd` → 重启后 `GET /api/operation-executions/<id>` 显示 `interrupted_at=…`（r0 state 保留原值）。

### 通知验收 N1~N11 证据索引
- **N1 stdout 生成通知**：各操作执行后 topics 列表出现对应 operation topic，详情含 extension 写入的 info/success/warning 多条。
- **N2 stderr 不生成通知**：`stderr-test-ext` 向 stdout 打 `::notify:: warning "stdout persists per protocol"`、向 stderr 打 `::notify:: error "stderr should NOT persist"` → topic 仅 1 条（warning），`notification_count=1`，error 未落库。
- **N3 每条 notify 一条不可变 Notification**：topic `last_seq` 连续 1~5，DB `select count(distinct id) from notification` = `count(*)` = 31。
- **N4 自动进入 Operation Topic**：操作执行的通知全部进入该操作关联的 `kind=operation` topic；`last_source_type=extension`。
- **N5 无 notify-to/写 API**：`POST /api/notifications` 与 `POST /api/notifications/topics/{id}/notifications` 均返回 `404`；`server.go` 中该写通知路由仅存于注释（"均被否定"），无实际注册。
- **N6 通知来源不可伪造**：脚本只输出 content/level，落库 `source_type/extension_name/action_id/run_id` 由 supd 闭包填充（seq4 记为 `extension_name=operation-responder-ext` 等）。
- **N7 超长行不堵塞**：`longline-test-ext` 输出约 0.5MB 单行 `::notify::` → 进程 `state=success` 正常终态，topic `notification_count=0`（`protocol.go` 8192 字节上限截断，不生成通知）。
- **N8 队列满/SQLite 慢不阻塞 Run**：由 `internal/store/writer.go`（有界队列 + `tryEnqueue` 满时 `dropped++` 非阻塞）+ `store_test.go` 队列满断言覆盖；E2E 侧以"磁盘只读时 Run 仍 success"佐证（见异常路径3）。
- **N9 Topic 删除/重启已读恢复**：`DELETE /api/notifications/topics/{id}` 后列表移除（软删）；topic 已读 `POST read` 返回 `read_seq=5`、`unread=0`；重启后 `read_seq` 仍为 5（统一游标持久化）。
- **N10 changes epoch/全量重同步**：无变更时 `GET /api/notifications/changes?epoch=<当前>&wait=` 返回 `reload:false`+同 epoch；有变更时 `reload:true` 且 `seq` 前进（26→36）。
- **N11 普通服务长期 Topic**：由 `store/notify_default.go` 的 `TryAppendToDefaultTopic` + `ensureDefaultTopic`（按 kind/source 复用、关闭时不关）+ `TestDefaultTopicCreateAndReuse` 覆盖；E2E 未单独用服务 stdout 复现（python 服务未注入 notify），如实记录为"由代码+单测确认"。

### 异常路径（§十 Phase 3.6）
1. **重启 + 数据库恢复**：`kill -9` 后重启，`<baseDir>/data/supd.db` WAL 恢复成功，13 topic/31 通知全部在（无数据丢失）。
2. **WAL 残留恢复**：kill -9 后 `supd.db-wal` 仍存在，重启后 DB 打开成功、数据完整（WAL checkpoint 正常）。
3. **磁盘只读**：对 data 目录 `chmod a-w` 后触发操作，Run 仍 `state=success`（写失败不阻塞 Run，通知丢弃不明显影响服务，符合 N8/writer 设计）。**如实注明**：因进程句柄已打开、已打开 fd 在目录只读时仍可写，无法在本环境真正"填满磁盘"触发确定性写失败；完整磁盘满验证依赖发布/CI 环境，**未执行**。
4. **writer 队列满**：单测覆盖（`store_test.go` 队列容量/满返回 false），E2E 未强制复现。

### 超大参数约束
`POST /api/operations/check-software/run` 传 >8KB params（`{"padding":"x"*10000}`）→ 返回 `400 {"code":"INVALID_REQUEST","message":"operation params invalid: params exceed 8192 bytes"}`。
