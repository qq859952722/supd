# 2026-09-01 会话

## smartdns 服务 failed 排查与修复（190 切换 Debian 底包引发）

### 触发原因

用户反馈 192.168.31.190:7979 的 smartdns 服务突然报错（此前一直正常运行），怀疑新代码引入回归。

### 排查过程与根因

- API 查询：smartdns `status=failed`，配置 `command: [bin/smartdns, -c, config/smartdns.conf, -f]`、`workdir` 空（CWD=服务根）。
- 事件环形缓冲显示 **08:53:21 supd 整体重启**（用户切换 Debian 底包重建容器的时间点），autostart 服务并行启动；08:53 三次启动失败均报 `fork/exec /etc/supd/services/smartdns/bin/smartdns: no such file or directory`，但 09:00 前日志证明 05:39 服务仍正常。
- 文件树确认 `bin/smartdns`（678904 字节）与 `bin/smartdns_ui.so`（5109848 字节，与官方 Release48.2 包完全同大小）**均存在** → 排除 supd 路径解析回归（解析路径本身正确）。
- **根因**：musl 链接的 smartdns 在 Debian(glibc) 底包下 execve 报 ENOENT（ELF 解释器 `/lib/ld-musl-x86_64.so.1` 缺失的经典假象）。与 supd 代码无关。

### 修复过程（两层问题，两步修复）

1. **解释器缺失**：通过一次性扩展（tjs）执行 `apt-get install -y musl`；Debian musl 包只提供 `/usr/lib/x86_64-linux-musl/libc.so` 且**不自动创建解释器符号链接**，手工 `ln -sf` 后 exec 通过。注意脚本 bug：`ln -sf <libc> /ld-musl...`（丢 `/lib` 前缀）创建到根目录导致校验失败，修正为 `/lib/ld-musl-x86-64.so.1`。
2. **符号不匹配**：exec 通了之后出现 `Error relocating ... SSL_CTX_ctrl: symbol not found` 等——musl loader 误加载 glibc 版 libssl。修复：本地解包官方 `x86_64-linux-all.tar.gz`，将同源 musl 版 `libssl.so.3`/`libcrypto.so.3`/`libgcc_s.so.1` 经 base64+文件 API 离线通道上传（190 无法直连 GitHub），由一次性扩展解码安装到 `bin/lib/`。smartdns 二进制带 `RPATH($ORIGIN/lib)` 自动命中，**无需 env 注入**（env.yaml PUT 返回 422，但已不必要）。
3. **结果**：smartdns 恢复 `ready`（pid 704）。日志中 `pending DNS server ... failed`（cloudflare/odvr.nic.cz DoH 上游）为上游网络可达性问题，smartdns 自动重试，与本次问题无关。
4. 一次性扩展 `smartdns-runtime-fix` 用后已删除（204）。

### 关键技术点

- `execve` ENOENT 两种成因：文件不存在 vs ELF 解释器缺失（文件存在时也会报 ENOENT），用 `file`/`readelf -l` 看 interpreter 区分。
- musl loader 默认只搜 `/lib:/usr/lib`（或 `/etc/ld-musl-x86_64.path`），不搜 `/usr/lib/x86_64-linux-gnu`；Debian musl 包 path 配置可能兜底命中 glibc 库导致 relocating 错误。
- musl 静态主程序无法 `dlopen` musl 动态插件（官方静态 `smartdns-x86_64` 资产不适合有 UI 插件的部署）。
- supd 文件 API：GET/PUT 均为 JSON `{"content": string}`（文本语义），二进制经 UTF-8 会损坏；二进制传输用 base64 文本通道。任务日志 API 响应字段是 `lines`（非 `data`）。
- SSH（dropbear）在容器重建后 root 密码未清空导致空密码认证失败，本次全程改用 supd HTTP API + 扩展完成远程操作。
