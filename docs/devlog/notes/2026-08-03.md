# 2026-08-03

## 修复多服务同名扩展查找竞态 + v0.0.42 发版

### 触发原因

用户在 2026-08-02 会话末尾遗留「service-scoped 扩展触发端点 `POST /api/services/{svc}/extensions/{ext}/run` 在多服务同名扩展时返回 404」的已知 UX 缺陷。用户要求修复并通过充分运行状态测试、代码审计后升级版本推送到 GitHub。

通读代码后发现该缺陷的**实际影响远超偶发 404**——同一根因感染 7 处调用，其中 3 处是静默数据损坏/丢失：

| 调用点 | 后果 | 严重度 |
|--------|------|--------|
| `handleGetServiceExtension` | 偶发 404（GET 详情） | 🟡 flaky |
| `handleRunServiceExtension` | 偶发 404（POST 运行） | 🟡 flaky |
| `UpdateExtension(name, meta, service)` | 写错服务的 meta.yaml | 🔴 数据损坏 |
| `DeleteExtension(name, service)` | 删错服务的扩展目录（备份+rename） | 🔴 数据丢失 |
| `SaveExtensionEnv(name, envData, service)` | env 写错服务 | 🔴 数据损坏 |
| `RunExtension(...)` | 用错 Meta（被 handler 前置 404 拦截） | 🟡 latent |
| `GetExtensionStatus(name, service)` | 返回错服务的状态 | 🟡 latent |

### 根因

`ExtensionProvider` 接口只有 `GetExtension(name string)`，按名字查找返回首个匹配。实现遍历 `Discovery.Services`（Go map，迭代顺序随机），多服务同名扩展时返回项不确定。5 个带 `service` 参数的 provider 方法虽接收 service 但未用它做精确定位。

### 修复方案

**新增 `GetExtensionForService(service, name string) (*ExtensionInfo, bool)` 到接口**，实现按服务作用域精确查找（`Discovery.Services[service].Extensions[name]` 直接索引，无 map 遍历，结果确定）。

- `service != ""`：精确查找，杜绝随机匹配
- `service == ""`：退化为 `GetExtension(name)` 语义，保持导入预览等"任意作用域存在即可"场景向后兼容

### 关键技术点

- **Go map 迭代顺序随机化**：`for _, v := range map` 每次迭代的起始 bucket/offset 由运行时随机化，多服务同名扩展时 `GetExtension` 返回项不确定 → 偶发 404 + 静默误操作
- **service="" 退化语义**：导入预览 `handleImportExtension` 调 `GetExtension(meta.Name)` 检查"该扩展名是否已存在于任意作用域"——这是合理的 name-only 查找，新方法 service="" 退化保持此行为
- **全局 handler 无回归**：`handleGetExtension`/`handleUpdateExtension`/`handleExportExtension`/`handleImportExtension`/`handleRunExtension` 均操作全局命名空间（GlobalExts 中扩展名唯一），保持 `GetExtension(name)` 不变
- **生命周期触发不受影响**：dispatcher 的 `findMatchingExtensions` 按服务作用域精确匹配（pre_start/post_ready 等），原本就正确，只有 on-demand HTTP 触发端点有此 bug
