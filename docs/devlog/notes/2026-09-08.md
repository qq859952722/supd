## 通用操作插槽与消息中心方案设计

- **触发原因**：用户要求为 supd 设计不预置业务语义的全局操作注册、服务扩展批量调用和频道式消息聚合能力，并要求将完整方案写入 `tmp/` 后进行专业架构与工程评审。
- **完成要点**：
  - 形成 `config.yaml operations` + 服务扩展 `actions[].operation` 的最小注册模型。
  - 总控调用复用现有 on-demand 扩展执行链，通过 `SUPD_OPERATION`、`SUPD_OPERATION_PARAMS`、`SUPD_MESSAGE_CHANNEL_ID` 单向传参。
  - 扩展通过 stdout `::message:: <level> "<content>"` 向当前频道实时推送消息；消息不参与任务终态或调度。
  - 消息中心采用内存频道/消息、自增 ID、频道级已读和长轮询，不新增事件类型、数据库、SSE 或 WebSocket。
  - 专业复核发现初稿存在同名服务扩展并发 key 串线、普通服务频道所有权、ID 重启复用和 stdout 背压风险；已在设计稿第 20 节形成修订实施基线。
  - 第一阶段收敛为服务级操作绑定、stdout 频道消息及受信任调用方的独立消息 API；普通服务开放频道后置到 Unix Socket 身份方案。
- **修改文件**：
  - `tmp/extension-slots-message-center-design.md`
  - `docs/devlog/notes/2026-09-08.md`
  - `docs/devlog/session-notes.md`
- **关键技术点**：并发追踪 key 必须调整为 `(service_name, extension_name, action_id)`；Run ID 必须贯穿 API、TaskManager、Executor 和消息来源；消息 Publish 必须非阻塞并设全局字节/条数预算。
- **遗留事项**：当前仅完成设计，尚未修改需求规格和源码；实施前须先将获批契约同步到需求规格与 Skill 文档。

## 操作中心与通知中心方案重新命名及二次审计

- **触发原因**：用户确认“插槽/消息”只是临时描述，要求两个模块重新命名、各自提供独立入口和页面，并将通知写入严格限制为受管进程 stdout。
- **完成要点**：
  - 正式命名为“操作中心（Operation Center）”和“通知中心（Notification Center）”。
  - 操作中心使用 `operations` + `actions[].operation`，支持全局扩展执行一次、服务级扩展逐个执行。
  - 通知仅支持 `::notify::` 和 `::notify-to::` stdout 指令；取消 HTTP、UDS、共享内存和文件通知写入入口。
  - 通知使用 UUIDv7 Topic/Notification、Topic 内 seq、持久化已读游标、JSONL journal 和 state 快照。
  - 两路独立审计发现并修正：普通服务延迟通知与 Topic 关闭冲突、Execution 重启恢复、journal 压缩竞态、删除后复活、stdout Scanner/背压、同名服务扩展并发隔离及全局扩展重复执行风险。
  - 最终将 Topic 定义为持久开放容器，Operation Execution 结束不关闭 Topic；采用单写 actor 保证 journal、内存、change、已读与压缩顺序。
- **修改文件**：
  - `tmp/operation-notification-center-design.md`
  - `docs/devlog/notes/2026-09-08.md`
  - `docs/devlog/session-notes.md`
- **关键技术点**：实施必须先完成 Phase 0，包括 tracker key 增加 service、stdout 持续排水、多 result 阻塞修复、统一 Run 提交/终态回调和 runResults 无界增长处理。
- **遗留事项**：方案为有条件通过；尚未更新需求规格、Skill 和源码。

## 操作中心注册方式简化及第三轮方案审计

- **触发原因**：用户要求取消独立全局操作配置，改为全局扩展 action 的 `operations` 属性自动注册，并要求全局 action 阶段先于服务扩展阶段；通知继续只使用 stdout。
- **完成要点**：
  - 重新生成 v3 设计稿：`tmp/operation-notification-center-design.md`。
  - 模块正式命名为“操作中心”和“通知中心”，分别提供 `/operations`、`/notifications` 独立页面。
  - `operations` 改为 action 级字符串数组；全局扩展负责注册按钮，服务扩展负责响应；同一全局扩展内禁止重复 ID，不同全局扩展同 ID 合并为一个操作。
  - 明确两阶段执行：全局扩展按稳定顺序先执行，全部终态后再执行服务扩展；业务协作仍由脚本和缓存文件自行控制。
  - 通知仅支持 stdout `::notify::` 与 `::notify-to::`；Topic 持久开放，使用 UUIDv7 和 Topic 内 seq，JSONL journal 与已读游标持久化。
  - 组织架构审计和工程审计，确认现有实现必须先完成并发作用域、stdout 排水、统一 Run 生命周期、持久化 actor/压缩、runResults 内存治理等 Phase 0。
