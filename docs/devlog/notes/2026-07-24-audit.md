## 一、真实 Bug（静态审计发现，✅ 已全部修复）

### [JS][P0] 1. `runCmd` 顺序读 stdout → stderr 存在管道死锁风险 ✅ 已修复
位置：`transmission-updater/run.js` `runCmd`

若子进程在 stdout 关闭前、向 stderr 写入超过管道缓冲（~64KB），写端阻塞 → 死锁。`tar`/`unzip`/`chown` 输出几乎都在 stderr。

**修复**：改为 `Promise.all` 并发读取两路流后再 `wait()`。

### [JS][P0] 2. 版本号比较永远不相等（"已是最新" 分支永不触发） ✅ 已修复
位置：`getLatestRelease` vs `getCurrentVersion` vs `doCheck`

原始 `getLatestRelease` 对 `"v4.1.3"` 标签保留 `v` 得到 `"v4.1.3"`，`getCurrentVersion` 正则得 `"4.1.3"` → 永不相等。

**修复**：`getLatestRelease` 先 `.replace(/^v/, '')` 去掉 v 前缀，再用与 `getCurrentVersion` 一致的 `\d+\.\d+\.\d+` 正则提取核心版本号，确保口径完全一致。

### [JS][P1] 3. `findFile` 匹配正则可能选中非二进制文件 ✅ 已修复
位置：原 `findFile` matcher `/^transmission-daemon.*[^.]$/`

`[^.]$` 允许以任意非点字符结尾，可能误选 `.sig/.txt` 等文件。

**修复**：改为 `matcher` 谓词精确判定——`name.startsWith('transmission-daemon')` 且排除 `.b2sum/.sig/.sha256/.sha512/.txt/.md/.tar/.xz/.zip/.json/.asc/.sha` 等扩展名。

### [JS][P1] 4. `setupDirectories` 未校验 `chown` 结果 ✅ 已修复
位置：`setupDirectories`

若 supd 非 root 运行，`chown -R` 静默失败 → 目录权限问题。

**修复**：检查 `runCmd` 返回的 `exitCode`，失败时输出 `::result:: warning` 提示权限风险。

## 二、运行测试阶段新增发现的真实 Bug（静态审计未覆盖，✅ 已全部修复）

说明：以上为静态审计结论。随后在真实 tjs 26.6.0 运行时执行 `transmission-updater`（见测试方案 `2026-07-24-testplan.md`），暴露 3 个静态审计无法发现的运行时 bug，均已修复：

### [JS][P0] 5. `tjs.readDir` 返回 DirHandle 而非数组（运行时 "value is not iterable"） ✅ 已修复
位置：`run.js` 原 `findFile` / `copyDir` 旧实现 → 新增 `listEntries()` 兼容层

静态审计未触及此路径（未实际运行 tjs）。运行测试发现 tjs 26.6.0 的 `tjs.readDir(dir)` 返回 **DirHandle**（异步可迭代对象），而非数组/字符串列表。原代码直接 `for...of` 迭代 → 抛出 `value is not iterable`，导致 install-update 在解压后递归查找二进制时崩溃。

**修复**：新增 `listEntries(dir)` 兼容层，检测 `Symbol.asyncIterator` 后用 `for await...of` 迭代 DirHandle，统一返回 `[{name, isDir}]`；并对「数组 / 以文件名为 key 的对象」两种形态做兜底。

### [JS][P0] 6. `DirHandle` entry 的 `isDirectory` 为布尔 getter（误判目录） ✅ 已修复
位置：`listEntries` 内 entry 属性判断

某些 tjs 实现中 `isDirectory`/`isFile` 是**布尔 getter 属性**而非方法。初版 `listEntries` 用 `!!ent.isDir`（字段不存在→undefined→false）误判 `out/` 为文件，导致二进制漏检（"压缩包中未找到 transmission-daemon 二进制"）。

**修复**：优先级 `ent.isDirectory()` → 回退 `!ent.isFile()` → 最后 `!!ent.isDirectory`（getter）。

### [JS][P0] 7. `transmission-daemon --version` 输出到 stderr（版本解析失败） ✅ 已修复
位置：`getCurrentVersion` / `runCmd`

`transmission-daemon --version` 将版本信息写到 **stderr**（stdout 为空）。原 `getCurrentVersion` 仅解析 `stdout` → 解析为 `unknown`，进而 "已是最新版本 vunknown" 与 "发现新版本" 逻辑混乱。

**修复**：`getCurrentVersion` 合并 `stdout + stderr` 解析 `\d+\.\d+\.\d+`。

## 三、设计完善性 / 潜在缺陷（P2 改进项，本次未修复，非崩溃）

### [Go][P2] 8. CPU 使用率在缓存未命中时恒为 ~0（测量缺陷）
位置：`resource_collector.go` getProcess 预热 + collectProcessResources

gopsutil `CPUPercent()` 首次调用建基线返回 0；自动刷新下首屏/进程重启后 CPU 长期偏低。

**建议**：移除多余预热，或前端标注"首次采样无效"，或基于 `/proc/stat` 进程时间差自行计算。

### [Go][P2] 9. context 超时对 gopsutil 调用无实际约束力（已知取舍）
位置：`resource_collector.go` 多处

`context` 仅用于 `ctx.Err()` 抽查；gopsutil 内部 `/proc` 读取无独立超时。属已记录的设计取舍，建议文档注明。

### [Go][P2] 10. 进程树仅两层（主进程+直接子进程），非真正的树
位置：`collectProcessTree` / `collectProcessTreeByCommand`

`gopsutil.Children()` 与 `findChildProcesses` 均只取**直接**子进程，不递归。前端标题"进程树"但实际为扁平列表。

**建议**：递归收集全树，或在文档/UI 明确"仅显示主进程与直接子进程"。

### [Go][P2] 11. `collectProcessTreeByCommand` 仅取第一个匹配进程（潜在串扰）
位置：`resource_collector.go` 的 `break`

按 `cmdBase` 子串匹配，命中第一个即 `break`。多实例服务会返回错误实例数据。

**建议**：结合主进程 PID / 父子关系进一步确认匹配。

### [Go][P2] 12. 降级路径 `ResourceResponse` 缺 CPU/内存占比（展示不一致）
位置：`resource_handler.go` 降级分支

降级时只 `sum MemoryMB` 与 `ProcessCount`，`CPUPercent/MemoryPercent` 为空。

### [JS][P2] 13. `downloadFile` 全量缓冲于内存（大文件风险）
位置：`run.js` downloadFile

先收集整个响应体进 `chunks` 再拼接写盘；对 >50MB 的 GitHub release 资产有内存压力。

**建议**：边读边写（若 tjs 支持流式写）。

### [JS][P2] 14. `tracker-updater` 硬编码 RPC 端口/无鉴权（健壮性）
位置：`tracker-updater/run.js` `RPC_URL = 'http://127.0.0.1:9091/transmission/rpc'`

未读取 `settings.json` 的 `rpc-port`，未处理 `rpc-authentication-required`。当前默认配置恰好关闭鉴权、端口 9091，故可用；用户改动后即失效。

**建议**：从 `config/settings.json` 读取 `rpc-port`（及凭证）。

### [JS][P2] 15. 依赖外部命令未校验存在性（健壮性）
脚本依赖 `tar`/`unzip`/`chown`/`uname`。极简环境（distroless）缺失会失败。属设计取舍（注释已说明），建议在文档/前置检查中声明依赖。
