## 端口交叉归属问题排查（transmission 显示 8080）
- **根因**：188 容器内 `yama ptrace_scope=1` → `readlink /proc/<pid>/fd/*` 对 `nobody` 进程返回 Permission denied（即使 root 也被拒）→ supd inode 精确匹配路径完全失败 → 走 UID 降级路径 → **qbittorrent-nox (pid=271, UID=65534) 和 transmission-daemon (pid=307, UID=65534) 都以 nobody 运行** → UID 匹配把所有 UID=65534 的端口归到两个服务上 → 8080（qbittorrent WebUI）被错误归属到 transmission。
- **真正监听 8080 的进程**：qbittorrent-nox `--webui-port=8080`（pid=271）。transmission 的 RPC 端口是 9091，peer 端口是 51413。
- **代码位置**：`port_collector.go` L52-95 `collectProcessPorts()` → L63-79 UID 降级分支 → `matchNetSocketsByUID()` 按 fields[7]（uid列）匹配 `/proc/net/{proto}`。
- **影响范围**：同一 UID 的所有服务端口列表互相串扰（nobody 用户的 qbittorrent/transmission 端口全部混在一起）。

## 端口交叉归属修复：UID 降级路径添加 cmdline 交叉验证
- **改动**：`collectProcessPorts(pid int)` → `collectProcessPorts(pid int, cmdPattern string)`
- **新增函数**：`collectInodesByCmdlineUID(uids, cmdPattern)` — 扫描 `/proc` 找所有 UID 匹合且 cmdline 包含 cmdPattern 基础名的进程，对其再次尝试 `collectSocketInodes`，缩小端口归属范围
- **新增辅助**：`cmdPatternFromConfig(cfg)` — 从 `ServiceConfig.Command[0]` 提取命令模式
- **降级层级**：
  1. 主路径：inode 精确匹配（readlink /proc/<pid>/fd → socket inode）
  2. 降级1：UID + cmdline 交叉验证 → 对 cmdline 匹合的进程重试 inode → 如果有 inode 结果，精确匹配
  3. 降级2：纯 UID 匹配（最终兜底，日志 Warn 级别提示可能串扰）
- **修改文件**：port_collector.go、service_handler.go、resource_handler.go、port_collector_test.go
